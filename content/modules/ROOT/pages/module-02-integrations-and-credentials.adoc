= Getting started: integrations and credentials

== What you will do

In this module you build the two integrations the rest of this lab
depends on:

* An *MCP Server* integration pointing at the Ansible Automation
  Platform (AAP) MCP server, which is what lets a task agent step list
  job templates and read inventory
* An *LLM Provider* integration pointing at the model service, which
  gives your task agent steps a model to reason with. This lab uses
  `qwen3-235b`

Along the way you will:

* Create an API token in Ansible Automation Platform
* Create two automation orchestrator credentials, one for each
  integration
* Validate both integrations so they report *Available*

[TIP]
====
Stuck at any point in this lab? Automation orchestrator has a
*solutions* project containing a complete, working, published copy of
everything you are asked to build. Switch the *Project* selector to
`solutions` and compare. For this module, look at the integrations named
*Solutions AAP MCP* and *Solutions LLM*. They are the finished version
of what you are about to create.
====

== Before you start: create an AAP API token

The AAP MCP server authenticates with a bearer token issued by Ansible
Automation Platform. This token allows for automation orchestrator to
use MCP tools that directly can call AAP for specific information. For
example, if you wanted your task agent to have information about the
existing job templates available or the hosts available within AAP.

. Open the *AAP* tab and log in as `{aap_controller_admin_user}` /
  `{aap_controller_admin_password}`.

. In the left navigation, expand *Access Management* and click
  *API Tokens*.
+
image::module-02/01-api-tokens-nav.png[title="", link=self, window=blank, width=100%]

. Click *Create token*. Fill in the form:
+
--
* *Description*: `Student AAP MCP Token`
* *Scope*: `Write`
--
+
Leave *OAuth application* empty, then click *Create token*.
+
image::module-02/02-create-api-token.png[title="", link=self, window=blank, width=100%]

. The *Token information* dialog appears. Click the *copy* icon to the
  right of the token value, then paste it somewhere you can get back
  to, such as a text editor or a scratch file in the terminal tab.
+
image::module-02/03-copy-token.png[title="", link=self, window=blank, width=100%]
+
[IMPORTANT]
====
This is the only time Ansible Automation Platform will show you this
token. Paste it somewhere before you close the dialog. If you close it
without copying, the value is gone and you have to delete the token
and create a new one.
====

== Log in to automation orchestrator

Login to the automation orchestrator with the following credentials.

[cols="1,3"]
|===
|URL |{ao_url}
|Username |`{ao_admin_user}`
|Password |`{ao_admin_password}`
|===

[NOTE]
====
You will notice there are already integrations and credentials in this
environment: *AAP*, *Lightspeed MCP*, *OpenFlake MCP*, *Solutions AAP
MCP* and *Solutions LLM*. Those belong to the `solutions` project and to
the pre-built reference workflows. Leave them alone. Everything you
create in this module is yours, named with a `Student` prefix, and lives
in the `default` project.

In automation orchestrator, credentials are scoped to a single project.
A credential in `solutions` cannot be used by a workflow in `default`,
which is exactly why you have to build your own.
====

== Create the credentials

The two credentials you will be creating are the AAP MCP credential and
the LLM credential. The AAP MCP credential requires the previously
copied AAP token to complete this section.

=== The AAP MCP credential

. In the left navigation, open *Credentials*. Confirm the *Project*
  selector at the top reads `default`, then click *Create credential*.
+
image::module-02/04-ao-credentials-list.png[title="", link=self, window=blank, width=100%]
+
[WARNING]
====
Check the *Project* selector before you create anything. A credential
created in the wrong project cannot be moved, and the workflows you
complete in later modules all live in `default`.
====

. Fill in the *Create credential* form:
+
--
* *Name*: `Student AAP MCP Credential`
* *Project*: `default`
* *Credential type*: `HTTP Bearer Token`
--
+
image::module-02/05-create-credential.png[title="", link=self, window=blank, width=100%]

. Paste the AAP token you copied into the *Token* field, then click
  *Create credential*.
+
image::module-02/06-paste-token.png[title="", link=self, window=blank, width=100%]

=== The LLM credential

. Click *Create credential* again. This time:
+
--
* *Name*: `Student LLM Credential`
* *Project*: `default`
* *Credential type*: `LLM Provider`
--
+
image::module-02/07-llm-credential-type.png[title="", link=self, window=blank, width=100%]
+
[NOTE]
====
*LLM Provider* is its own credential type, not an HTTP bearer token.
Picking the wrong type here is the most common mistake in this module.
The integration wizard filters the credential list by type, so a
miscreated credential simply will not appear when you go looking for
it.
====

. Choosing *LLM Provider* replaces the *Token* field with an *API Key*
  field. Paste the LLM API key into it and click *Create credential*:
+
[source,text,role=execute]
----
{litellm_virtual_key}
----

. Both credentials now appear in the list, scoped to the `default`
  project.
+
image::module-02/08-credentials-done.png[title="", link=self, window=blank, width=100%]

== Create the AAP MCP server integration

With the credentials in place, you will now create the integration for
AAP MCP and LLM.

. In the left navigation, open *Integrations* and click
  *Configure integration*.

. On step 1, *Integration details*, fill in:
+
--
* *Integration type*: `MCP Server`
* *Server name / ID*: `Student AAP MCP Server`
--
+
and paste this into *API URL*:
+
[source,text,role=execute]
----
{aap_mcp_url}
----
+
Leave *Scope* set to *Global* and click *Next*.
+
image::module-02/09-mcp-details.png[title="", link=self, window=blank, width=100%]
+
[NOTE]
====
The `/mcp` on the end of the URL is a required portion of the endpoint.
Without it, the connection test fails.
====

. On step 2, *Connection credential*, select
  *Student AAP MCP Credential* from the *Health check credential*
  dropdown, then click *Test connection*.
+
image::module-02/10-mcp-credential.png[title="", link=self, window=blank, width=100%]

. A green *Connection tested* notification confirms the connection and
  reports how many tools it discovered: 144 of them, the full AAP API
  surface. Step 3, *Enable tools*, lists them all with every box ticked.
  Leave them as they are and click *Save integration*.
+
image::module-02/11-enable-tools.png[title="", link=self, window=blank, width=100%]
+
[NOTE]
====
Enabling all 144 tools here does not hand them to your task agent
steps. It only decides what is *available* to pick from. In later
modules, you will choose a specific pair of tools for one agent, and
enabling everything now is what makes that choice possible later.
====

and paste this into *API URL*:
+

Click *Next*.
+
image::module-02/12-llm-details.png[title="", link=self, window=blank, width=100%]

. On step 2, *Connection credential*, open the *Health check credential*
  dropdown and select *Student LLM Credential*, then click
  *Test connection*.
+
image::module-02/13-llm-credential.png[title="", link=self, window=blank, width=100%]
+
[NOTE]
====
Only credentials of type *LLM Provider* appear in this list. If
*Student LLM Credential* is missing, you created it as an HTTP Bearer
Token. Go back to *Credentials* and make a new one with the right

====

. The connection test reports *Discovered 1 model*. On step 3,
  *Enable models*, `qwen3-235b` is listed and ticked. Click
  *Save integration*.
+
image::module-02/14-enable-models.png[title="", link=self, window=blank, width=100%]
+
[TIP]
====
Nothing ties automation orchestrator to this particular model. Any

integration can point at whatever your organization already runs.
====

. Both of your integrations now appear in the list alongside the
  pre-built ones.
+
image::module-02/15-integrations-done.png[title="", link=self, window=blank, width=100%]

== Validate both integrations

Look at the *Status* column. A freshly created integration reads
*Unknown* until you explicitly validate it.

. Find *Student LLM* in the list. Click the *⋮* menu at the right end of
  its row and choose *Validate integration*.
+
image::module-02/16-validate-integration.png[title="", link=self, window=blank, width=100%]

. The status flips to *Available* and *Last checked* fills in with a
  timestamp.
+
image::module-02/17-validate-result.png[title="", link=self, window=blank, width=100%]

. Do the same for *Student AAP MCP Server*: *⋮* → *Validate
  integration*.

`Student LLM Credential` (LLM Provider), both *Enabled*

[NOTE]
====
If an integration still reads *Unknown* after validating, open it and
re-run *Test connection*. The usual causes are a missing `/mcp` suffix
on the AAP MCP URL, or an AAP token that was never actually copied out
of the dialog.
====

== What you learned

* Integrations are *connections*; credentials are *secrets*. They are
  separate objects so one credential can serve several integrations, and
  so rotating a secret does not mean rebuilding a connection.
* Credentials are scoped to a single project. This is why the `default`
  project needs its own copies even though `solutions` already has
  working ones.
* The *credential type* has to match what the integration expects. An
  LLM Provider integration will not see an HTTP Bearer Token credential.
* Discovery is what makes an integration useful: the MCP integration
  found 144 callable tools and the LLM integration found 1 model, and
  those are what you will wire into task agent steps in the modules
  ahead.

In the next module you put both of these to work, building a workflow
from an empty canvas.
