= Ticket enrichment workflow

== What you will do

The previous workflow exercise focused on disk utilization remediation
using a webhook trigger, a switch step, and deterministic AAP job
templates. Building on those concepts, the ticket enrichment workflow
introduces task agents to evaluate incidents, recommend actions, and
determine the appropriate remediation path. It also demonstrates how
automation orchestrator integrates with an ITSM ticketing service such
as OpenFlake to enrich incidents and record the results of automated
actions.

* The *auto remediate* path is taken when a low risk, high priority
  incident with a pre-approved job template exists to fix the issue.
* The *needs approval* path is taken when a fix exists but carries risk,
  thus human approval is required (human in the loop).
* The *inform only* path is taken when no remediation exists or
  additional information is needed.

All three paths use an AAP job template to post the findings and
outcome back into the OpenFlake ticket automatically. The *Auto
Remediate* and *Needs Approval* paths also run remediation job
templates, while *Inform Only* updates the ticket without attempting
remediation.

== Authorize the webhook trigger

This workflow does not start with somebody clicking *Run*. It starts
when Ansible Automation Platform posts to a URL. A webhook trigger will
not accept that post from just anyone, so it needs to be told which
service account is allowed to call it. This is what keeps an endpoint
that can launch real automation from being something anyone who finds
the URL can fire.

. Click the *OpenFlake Trigger* step. Open the *Authorized service
  accounts* dropdown and tick *aap-student-webhooks*.
+
image::module-05/02-webhook-service-account.png[title="", link=self, window=blank, width=100%]

. The dropdown now reads *1 selected* with the account listed beneath
  it. Click *Update*.
+
image::module-05/03-service-account-selected.png[title="", link=self, window=blank, width=100%]

[NOTE]
====
The *Webhook path* field above it reads `student-openflake-incident`.
That path is what makes the endpoint yours. The copy in the `solutions`
project answers on `openflake-incident`, and a webhook path has to be
unique across the whole instance, so the two cannot collide.
====

The agent's prompt walks it through exactly two lookups: read the
incident out of OpenFlake with `perform_query`, then list what AAP can
run with `job_templates_list`. Narrowing a task agent's list of tools
enables it to focus on specific tools needed to complete a task versus
attempting to use additional non-relevant tools.

[NOTE]
====
`job_templates_list` is what turns this from a guess into a
recommendation. The agent does not invent a remediation. It reads the
real list of job templates out of Ansible Automation Platform and picks
one by name, and if nothing
on that list genuinely fixes the incident it is required to route to
*Inform Only*.
====

=== Inform Only

*inform_only* raises an incident that nothing in AAP remediates. The
triage agent routes it to the *Enrich and Assign* agent, which is why
that second agent needed a model. The ticket ends up annotated and
*In Progress* rather than resolved, waiting for a person.

. Relaunch *Ticket Enrichment Simulate Alert* one more time. Set
  *What scenario to run?* to *inform_only*, leave
  *Which workflow should this fire?* on
  *student - the workflow I built*, and launch it.
+
image::module-05/27-inform-only-survey.png[title="", link=self, window=blank, width=100%]

. Open the new incident in OpenFlake. This one is a security incident:
  repeated failed SSH logins from multiple external addresses. There is
  no job template in Ansible Automation Platform that remediates a
  brute force attack, and the description says so outright.
+
image::module-05/28-openflake-security.png[title="", link=self, window=blank, width=100%]

. Follow the run in automation orchestrator. It completes without
  pausing, and the path through the canvas is different again:
  *Route Decision* took the *Inform Only* port into *Enrich and Assign*,
  the second task agent, and then into a final ticket update. No
  remediation job ran at all.
+
image::module-05/29-inform-only-run-complete.png[title="", link=self, window=blank, width=100%]

. Back in OpenFlake, the ticket is *In Progress* rather than
  *Resolved*. The triage agent's work note says why it chose this route:
  no automated remediation template matches, so no automated actions
  will be taken. Underneath it, the *Enrich and Assign* agent has left a
  handoff for the security team with concrete investigation steps, and a
  customer-facing comment at the bottom.
+
image::module-05/30-openflake-handoff.png[title="", link=self, window=blank, width=100%]

[NOTE]
====
Nothing was fixed here, and that is the correct outcome. The agent was
required to route to *inform only* the moment it could not name a real
job template, no matter how serious the incident looked. What it did
instead was provide detailed analysis on how the issue should be
addressed.

== What you learned

* A task agent is only as useful as the *tools* you connect it to.
  Selecting a tool and authenticating to the server that provides it are
  two separate actions, and the agent is not usable until you have done
  both.
* Pinning an agent to the exact tools its prompt names is a design
  choice, not a limitation. Two tools, two calls, one decision.
* A *webhook trigger* makes a workflow something other systems can
  start. It needs an authorized service account, and it only goes live
  when the workflow is published.
* A *switch* turns one agent's answer into three different paths through
  the same workflow, and an *approval gate* on one of those paths is how
  you keep a person in front of the changes that warrant one.
* Automation orchestrator *recommends*, Ansible Automation Platform
  *executes*. The agent chose the job template by name. AAP ran it, and
  AAP wrote the result back to the ticket.
