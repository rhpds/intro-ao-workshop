= Disk utilization remediation

== What you will do

In the previous module, you built a workflow from an empty canvas. In
this module, you'll start with an almost-complete workflow and build
the missing steps.

*Disk Utilization Remediation* starts when Ansible Automation Platform
sends a disk alert to a webhook. An AAP job template checks disk
utilization, and a *switch* uses the result to select the appropriate
route. Each route handles the result and posts a notification to a
Mattermost channel:

* *<80%* is healthy, so it records the check and does nothing else.
* *80-95%* is a warning, so it reclaims space by cleaning up old logs.
* *>95%* is critical, so it grows the volume rather than deleting
  anything.
* *Fallback* catches anything the three routes above do not match.

Three of the four routes are already configured. The *>95%* route is
missing its two steps. You'll add a remediation step to grow the
volume and a notification step to post the result to Mattermost. Use
the *80-95%* route directly above it as your example. It follows the
same pattern: remediate, then notify.

=== Adding the details into the extra variables

The existing job template, *Linux - Remediate - Disk Expand*, needs to
know the values to properly grow the filesystem. Re-open the
*Linux - Remediate - Disk Expand* job template and enter the variable
values that are captured at run time.

. Scroll down to *Extra variables* and type the skeleton, leaving the
  three values empty:
+
[source,json]
----
{
  "disk_tier": "",
  "disk_mount": "",
  "disk_use_percent": ""
}
----

. Now fill them in from the *Input* panel on the left. Expand
  *Launch AAP job template*, then *artifacts*. Because you ran the
  workflow once already, these are not placeholders: `disk_tier` reads
  `ok`, `disk_mount` reads `/`, and `disk_use_percent` reads the
  percentage from that run. Hover each one, click the copy icon, and
  paste it between the quotes after the matching key. This captures the
  appropriate value when the run uses the
  *Linux - Remediate - Disk Expand* job template.
+
image::module-04/13-extra-vars-skeleton.png[title="", link=self, window=blank, width=100%]

. All three values should be expressed as shown below.
+
image::module-04/14-extra-vars-filled.png[title="", link=self, window=blank, width=100%]
+
[NOTE]
====
Look at the shape of what you pasted:
[source,text]
----
${activity_61ac9127_f147_4fa8_9c04_189097e753e9.artifacts.disk_mount}
----
The tail, `artifacts.disk_mount`, is the name the check step's playbook
published. The long `activity_...` in the middle is that step's
generated id, which is why you copy these rather than type them.

=== Capturing the extra vars

The *Notify Chatroom* playbook takes the full set of values every
remediation branch publishes so that one playbook can render a card
for any of them. Copying large amounts of expressions out of the
*Input* panel manually is slow and tedious. The following script reads
your workflow, finds the step that is wired to the *>95%* route and
prints the whole block ready for you to copy and paste.

. Switch to the *Terminal* tab on the Showroom and point the script at
  your automation orchestrator. The last line prompts for the password, so nothing is
  echoed and nothing lands in your shell history. Paste
  `{ao_admin_password}` at the prompt and press kbd:[Enter].
+
[source,bash,role=execute,subs="attributes+"]
----
export AO_URL="{ao_url}"
export AO_USER="{ao_admin_user}"
read -rsp "AO password: " AO_PASS; export AO_PASS; echo
----

. Run it.
+
[source,bash,role=execute]
----
./ao-extra-vars
----
+
image::module-04/20b-extra-vars-script.png[title="", link=self, window=blank, width=100%]
+
[NOTE]
====
The two lines beginning with `#` are there to tell you which step the
script read from. They are not part of the answer. Copy only the JSON,
from the opening `{` to the closing `}`, as boxed in the image.
====

. Re-open the *Notify Chatroom* job template and copy that JSON into
  *Extra variables* on this step. Then click *Update*.

== What you learned

* A *switch* routes on a value an earlier step produced, and each route
  is a branch you wire independently. Three working branches beside an
  empty one is the easiest specification to build against.
* Running the healthy route gave you real output from the disk check
  step. You then used its published artifacts to configure the
  critical route without manually typing expressions.
* An extra variables expression is a *reference into the graph*, not a
  string. Automation orchestrator refuses to publish a branch that
  reads from a step it can never have run, which is a class of mistake
  you would otherwise find at three in the morning.
* Publishing makes your latest workflow changes available to the
  webhook. If you edit a published workflow, you must publish the new
  version before incoming alerts can use those changes.
* Automation orchestrator decided *which* remediation to run. Ansible
  Automation Platform ran it, measured the result, and reported it.
  Each did the part it is good at.
